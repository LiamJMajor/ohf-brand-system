# Principles

Every skill in this builder, and every file it produces, follows these. When a decision is unclear, come back here.

## 1. Agents first, humans second
Write every file so an agent can load it and act. Humans can still read it, but reading is not the primary path. This means: imperative instructions, concrete rules, explicit file pointers, no marketing prose about the brand.

## 2. Progressive disclosure
Three tiers. An always-loaded index of one line per entry. A skill body that loads on trigger. Reference files that load on demand. A task should touch a handful of files, never the whole repo. If a SKILL.md passes 300 lines, split it.

## 3. Taste stays human, repetition becomes software
Codify only decisions that are stable and proven. New identity work, campaign platforms, naming, sensitive announcements: these stay with people. Recurring outputs from settled decisions: these become skills.

## 4. Coherence over consistency
Consistency says we always look like this. Coherence says we evolve and you still know it is us. Define modes (quiet to loud) and the relationships between them, so automation does not scale sameness.

## 5. An undated fact is a rumour
Every product truth carries `valid_from`, `source` and `review_by`. Automation feeds truths where it can. Skills cite truths by path rather than restating them.

## 6. Examples beat rules
"Warm and approachable" teaches nothing. Three annotated examples of the real thing, with what makes each work, teach a model and a person in one pass. Prefer contrast pairs: this, not that.

## 7. Every correction becomes a commit
When someone fixes a draft, the fix goes into the repo the same day, in the right place: a truth, a rule, a skill instruction, or an example. A correction that lives only in Slack is gone by lunch.

## 8. Honest boundaries
A seventy percent result that a designer must rebuild under deadline is worse than no tool. Every skill states where it is reliable and what it routes to a person. Escalation rules are first-class files.

## 9. Run it like a product
Named owners. A review cadence. Evals that fail. A roadmap. Pruning. The team's value is how much judgment it made reusable, not how many requests it closed.

## 10. One shape for every project
Hundreds of projects, one directory schema, one validator. A project is defined by the same files with the same headings whether it is a flagship or a library nobody has heard of; only the tier changes what is required. Consistency is a failing check, not a review opinion. Skills are written per beat and take the project as intake, never per project.

## 11. Start narrow, measure pass-through
Pick the two or three requests that clog the queue most. Make them fully self-serve. Measure the share of outputs that ship without a human rebuild. Expand only when that holds.
